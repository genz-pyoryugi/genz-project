# 내 학습 기록 · 운영자 화면 설정

파트별 진행 상태와 ‘이어 풀기 / 처음부터 풀기’는 [퀴즈 진행 저장 안내](quiz-progress.md)를 따릅니다. `202610200002_quiz_progress.sql`의 실제 Supabase 적용과 진행 상태 버전 1을 확인했습니다. 답 선택 중 상태도 별도 진행 테이블로 동기화하며, 제출된 답안·최종 점수 집계는 기존 공식 채점 구조를 유지합니다.

## 구현된 화면

- `/quiz`: 완료 화면은 **AI 팀장 시뮬레이션**으로 이어집니다. 학습 기록은 `/learning`에서 조회합니다.
- `/learning`: 같은 브라우저의 익명 학습 기록을 직접 엽니다.
- `/admin/learning`: 미리 지정된 운영자가 이메일·비밀번호로 로그인합니다. 일반 학습자의 익명 세션과 다른 저장 키를 사용하며 운영자 세션은 해당 탭의 sessionStorage에만 보관합니다.
- 화면에 표시되는 응시와 집계는 저장된 Supabase 기록입니다. 빈 기록을 예시 데이터로 대체하지 않습니다.

## Supabase에서 직접 할 설정

1. 기존 프로젝트의 **Anonymous Sign-Ins**를 유지합니다. 환경 변수는 기존 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 두 개를 그대로 사용합니다. 관리자 화면에도 service-role/secret 키가 필요하지 않습니다.
2. SQL Editor에서 기존 두 마이그레이션이 적용되어 있는지 확인합니다.
   - `202610160001_learning_tracking.sql`
   - `202610160002_multi_choice_and_listing.sql`
3. **새 마이그레이션 `supabase/migrations/202610200001_learning_history.sql` 전체를 한 번 실행**합니다. 트랜잭션 단위이므로 중간 오류가 나면 롤백합니다. 이미 적용한 파일을 반복 실행하지 마세요. 기존 `quizzes`, 방문, 이벤트, 답안, 점수는 삭제하지 않습니다.
4. Supabase **Authentication → Users**에서 운영자용 이메일 계정을 직접 생성하거나 이미 신뢰하는 일반 이메일 계정을 선택합니다. 익명 계정은 운영자로 사용할 수 없습니다. 사용자 UUID를 확인하고 SQL Editor에서 아래 템플릿의 UUID를 교체하여 실행합니다.

   ```sql
   -- 아래 UUID는 예시입니다. 실제 운영자 Auth 사용자 UUID로 교체하세요.
   insert into public.lt_operators(user_id)
   select id from auth.users
   where id = '00000000-0000-0000-0000-000000000000'::uuid
     and not coalesce(is_anonymous, true)
   on conflict do nothing;

   -- 지정 결과 확인: 의도한 계정이 1행 있는지 확인하세요.
   select o.user_id, u.email, o.appointed_at
   from public.lt_operators o join auth.users u on u.id=o.user_id;
   ```

5. `/admin/learning`에서 그 계정으로 로그인합니다. 화면에 가입 버튼은 없습니다. 이메일 가입이 가능한 프로젝트라도 가입만으로는 `lt_operators`에 들어갈 수 없으므로 운영 권한을 얻지 못합니다. 익명 로그인이 필요하므로 전체 신규 가입을 무조건 끄지 마세요. `user_metadata`나 이메일 도메인으로 운영자를 지정하지 않습니다.
6. 새 SQL 적용 후 퀴즈 페이지를 새로고침합니다. SQL이 적용되지 않은 상태의 오답 복습은 이전과 같이 연습으로만 동작하며, 저장됐다고 표시하지 않습니다. 새 SQL이 확인되어야 오답 복습 기록을 전송합니다.

### 자동 저장과 기존 저장 실패 복구

답안의 ‘정답 확인’을 누르면 해당 답안을, 마지막 답안을 제출하면 응시 완료를 자동 전송합니다. 새로고침이나 재전송에는 원래 응시·이벤트 ID를 사용하므로 점수와 답안을 중복 추가하지 않습니다. 전송할 기록은 먼저 브라우저의 localStorage 대기열에 보관하며, 15초마다, 인터넷 재연결 시, 창으로 돌아올 때 자동 재시도합니다. 연결 설정 조회가 잠시 실패해도 다음 시도에서 다시 연결합니다.

이전 DB 규칙에서 거절된 퀴즈 이벤트는 새 SQL의 버전 3이 확인되면 동일 사용자·원본 ID·답안 그대로 한 번 재전송합니다. 다시 거절된 기록은 실패 안내를 유지합니다. 다른 익명 사용자의 기록은 재전송하지 않습니다. 과거에 저장하거나 수집하지 않은 답안을 생성하지 않으며, SQL 적용 전 연습으로만 진행한 오답 복습 기록도 만들어내지 않습니다. 복구 전에는 브라우저 데이터를 삭제하지 마세요.

읽기 전용 연결 점검: 프로젝트 폴더에서 `node --env-file=.env.local scripts/check-learning-storage.mjs`를 실행합니다. 키·토큰·학습자 기록은 출력하지 않고 익명 로그인 활성화, 공개 퀴즈 수, 학습 기록 함수 존재 여부를 확인합니다. 학습 기록 함수의 `PGRST202`는 SQL 미적용 또는 스키마 캐시 갱신 대기 상태이며, 권한 오류는 익명 API 키로 호출할 수 없기 때문일 수 있습니다. 실제 버전은 로그인된 앱이 확인합니다.

운영자 해제도 신뢰하는 SQL Editor에서 처리합니다. 다음 조회 요청부터 서버와 RLS에서 차단하며 JWT 갱신을 기다리지 않습니다.

```sql
delete from public.lt_operators
where user_id = '00000000-0000-0000-0000-000000000000'::uuid;
```

2026-10-20 연결 검증에서 실제 Supabase의 학습 기록 버전 3 적용을 확인했습니다. 마이그레이션은 사용자가 SQL Editor에서 적용하는 방식이며, 운영자 지정은 별도입니다. 확인용 익명 Auth 세션 하나를 생성해 본인 기록 조회와 저장 함수 권한을 확인한 후 로그아웃했습니다. 테스트용 방문·퀴즈 응시·답안·점수는 생성하지 않았습니다. 유효하지 않은 저장 요청이 DB 검증에서 거절되어 학습 데이터가 쓰이지 않는 것도 확인했습니다.

사이트 전체를 새로고침하여 새 저장 코드를 로드해야 합니다. 퀴즈 팝업을 닫았다 여는 것만으로는 부모 창의 기존 추적 코드가 바뀌지 않을 수 있습니다. 이미 연습으로 완료한 과거 오답 복습을 소급 저장하지 않으며, 새로 시작한 오답 복습부터 저장합니다.

## 데이터 재사용과 비교 기준

기존 `lt_visits`, `lt_events`, `lt_attempts`, `lt_answers`와 고정된 문제·퀴즈 버전을 재사용합니다. 기존 버전의 전체 응시에는 문제 구성 변경 방지 트리거가 이미 적용되어 있습니다.

- 새 응시: `lt_attempts.mode`로 `full`/`review` 구분, `source_attempt_id`로 복습 원본 연결, `lt_attempt_items`로 실제 출제 문항을 고정합니다.
- 과거 응시: 이전 코드가 저장한 것은 전체 응시뿐이므로 `mode=full`입니다. 과거에 저장하지 않았던 오답 복습은 새로 만들거나 추정하지 않습니다. 과거 문제 구성은 그때의 수정 불가능한 퀴즈 버전에서 읽습니다.
- 오답 복습 문항은 클라이언트 목록을 신뢰하지 않고 **본인 소유·완료된 원본 응시의 오답**에서 DB가 직접 결정합니다. 복습의 오답을 다시 복습하는 것도 같은 방식입니다.
- 비교는 조회 범위 안에서 **같은 방문자 + 퀴즈 버전 UUID + 실제 문제 버전 ID의 순서 + 응시 유형**으로 묶은 완료 기록만 사용합니다. 다른 버전, 전체 응시와 복습, 다른 복습 문항 구성은 별도 그룹입니다. 미완료 기록은 비교에서 제외하고 목록에는 남깁니다.
- 화면 점수는 DB가 채점한 문항별 배점 합계입니다. 정답·오답 수는 점수와 별개로 표시합니다. 미응답은 오답으로 추정하지 않습니다.
- 응시 날짜는 저장된 `started_at`입니다. 기존 추적 방식에 맞춰 응시는 첫 답안 제출 때 시작합니다. 클라이언트가 보고한 시각이므로 정확한 외부 시계나 노출 시간 측정값으로 간주하지 않습니다.

## 관리자 경로 분석

첫 화면 선택과 이용 경로는 별개의 값입니다. 첫 선택은 기존 `lt_visits.first_choice`를 그대로 보여 줍니다. 미수집이면 미수집으로 표시합니다.

경로는 같은 방문의 해당 `quiz_started` 이벤트보다 순번이 앞선 이벤트 중 마지막 `cardnews_opened`, `office_entered`, `office_object_opened`로 분류합니다. 카드뉴스면 **카드뉴스 → 퀴즈**, 사무실 입장/물건 열기면 **사무실 → 퀴즈**입니다. 선행 이벤트나 시작 이벤트를 확인할 수 없으면 **직접 진입·미분류**로 둡니다. 화면의 이용 순서에는 수집된 전체 이벤트를 순번·시각과 함께 표시합니다. 데이터가 없는 체류 시간이나 카드뉴스 완독을 만들어 내지 않습니다.

- 응시자 수: 해당 경로의 고유 익명 사용자 수. 사용자가 경로를 바꾸어 재응시하면 양쪽에 포함될 수 있습니다.
- 완료율: 완료된 전체 응시 수 / 시작된 전체 응시 수 × 100.
- 정답률: 완료된 전체 응시의 정답 수 합계 / 문제 수 합계 × 100.
- 오답 복습과 테스트 퀴즈는 이 세 경로 지표에서 제외합니다. 분모 0은 `—`입니다.
- 기간 필터는 KST 날짜이고 종료일을 포함합니다. 응시는 응시 시작일, 방문 목록은 방문 시작일 기준입니다. 주제·경로 필터가 있으면 방문 목록은 해당 조건의 응시가 있는 방문만 표시합니다. 필터 조건은 CSV에도 똑같이 적용됩니다.
- 집계는 현재 페이지 50건이 아니라 **필터에 맞는 전체 기록**을 사용합니다. CSV는 UI 페이지와 무관하게 단일 DB 조회 결과를 내보냅니다. 10,000응시/방문 초과 시 부분 파일을 만들지 않고 기간 축소를 안내합니다.
- 경로별 차이는 관찰 결과입니다. 버전·주제 구성, 재응시 횟수와 사용자 차이 등의 영향을 받을 수 있으며 **학습 효과나 인과관계가 입증됐다는 의미가 아닙니다.**

## 접근 권한과 중복 처리

- 브라우저는 공개 키와 본인의 Auth 토큰만 사용합니다. 서버는 `getSession()`의 사용자 정보나 클라이언트 전달 사용자 ID를 신뢰하지 않고 `auth.getUser(token)`으로 토큰을 검증합니다.
- 관리자 API는 매 요청마다 비익명 사용자 여부와 DB의 `lt_is_admin()`을 확인합니다. 전체 조회 RPC도 자체적으로 운영자 권한을 검사합니다. 원본 테이블과 invoker 뷰의 RLS는 소유자 또는 운영자에게만 기록을 허용합니다. 자기 기록 API는 운영자에게도 자기 기록만 반환합니다.
- `lt_operators`는 RLS가 켜져 있고 `anon`, `authenticated`, `public`의 권한이 없습니다. API로 본인을 임명하거나 다른 사람을 임명할 수 없습니다.
- 기록 API/CSV는 `private, no-store`와 `Vary: Authorization`으로 응답합니다. CSV는 UTF-8 BOM, 따옴표·줄바꿈 이스케이프와 수식 삽입 방지를 적용합니다.
- 응시·진행 상태는 해당 익명 사용자별 sessionStorage 키에 보관하여 새로고침 후 같은 응시 ID를 사용합니다. 버전이 달라졌으면 이전 상태를 새 문제에 적용하지 않습니다.
- 기존 영속 outbox를 계속 사용하며 이벤트 UUID, 응시 UUID, `(attempt_id, question_version_id)` 키와 사용자별 트랜잭션 잠금으로 재시도·동시 전송을 보호합니다. 서버에서 정답과 점수를 계산하고 같은 응시의 첫 답안만 받습니다. 완료된 응시의 동일한 답안/완료 재전송은 성공으로 처리하고 합계를 다시 늘리지 않습니다. 다른 답안으로 덮어쓰려 하면 거부합니다.
- 30분 뒤 새 방문이 시작되어도 이어 푸는 응시는 원래 방문 ID를 유지합니다. 영구 거절된 이벤트는 별도 보관하고 오류 안내를 유지해 성공으로 잘못 표시하지 않습니다.
- 익명 Auth 연결은 같은 브라우저 저장 공간에 의존합니다. 브라우저 데이터 삭제·시크릿 모드 종료·기기 변경 시 이전 사용자와 연결되지 않을 수 있으며 화면에도 안내합니다. 진행 상태 저장을 막은 브라우저에서는 새로고침 후 이어 풀기가 보장되지 않습니다.

관련 공식 문서: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [서버 인증에 쓰는 getUser](https://supabase.com/docs/reference/javascript/auth-getuser).

## 검증

`npm test`에서 테스트 전용 로컬 PostgreSQL 엔진(PGlite)에 `auth.uid()`/역할을 격리하여 모든 마이그레이션을 실제 실행합니다. 테스트용 데이터는 메모리 DB에만 생성합니다. API·CSV·새로고침 상태와 기존 추적기 회귀 테스트도 함께 실행합니다.

검증 항목은 익명 A/B 간 테이블·뷰·RPC 접근 격리, 비로그인 차단, 운영자 전체 조회/즉시 권한 회수, 익명 운영자 지정 무효화, 직접 점수 수정/자기 운영자 지정 차단, 과거 데이터 보존, 복수 선택/배점 채점, 복습 문항 제한, 버전·구성별 재응시 비교, 중복 저장/완료 방지, KST 필터·경로 분모·페이지 무관 집계, CSV 권한·이스케이프·완전한 필터 범위입니다.

실제 Supabase에서 확인한 사항은 기존 카탈로그 7개 주제 조회 성공, 비로그인 응시 테이블 조회 차단, 신규 RPC 미적용 상태입니다. 운영 환경의 두 익명 브라우저와 지정된 운영자 계정으로 최종 로그인/권한 검증은 새 SQL 적용 뒤 진행해야 합니다. 로컬 검증을 실제 운영 DB에 마이그레이션을 적용한 것으로 해석하면 안 됩니다.

기록 페이지와 관리자 로그인 페이지의 HTTP 200, 미인증 사용자·관리자 API/CSV의 HTTP 401도 확인했습니다. 브라우저 UI 도구가 Windows의 현재 URL을 확인하지 못해 화면 조작·스크린샷 검증은 중단됐습니다.
